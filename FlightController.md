### **1. Аппаратные платформы с открытым исходным кодом**
#### **Pixhawk (и его модификации)**
- **Описание:** Серия популярных контроллеров на базе ARM-процессора, разработанных сообществом PX4 и 3DR. Поддерживают множество датчиков (IMU, GPS, барометр) и интерфейсов (UART, CAN, I2C).
- **Примеры:**  
  - **Pixhawk 4**, **Cube Black**, **Cube Orange** (на базе STM32).  
  - **Pixhawk 6X** (поддержка до 6 UART, CAN FD, USB 3.0).  
- **Особенности:**  
  - Работают с прошивками **ArduPilot** или **PX4**.  
  - Подходят для профессиональных и любительских проектов.  
  - Широкая поддержка датчиков и модулей (LiDAR, оптические потоковые камеры).  

#### **F4/F7 Boards (например, Kakute F7, Matek F405)**  
- **Описание:** Дешевые и компактные платы на базе чипов STM32F4/F7, часто используются в гоночных дронах или малых БПЛА.  
- **Примеры:**  
  - **Kakute F7 AIO** (все в одном: регуляторы, OSD, Wi-Fi).  
  - **Matek F405-STD** (поддержка ESC, GPS, батареи).  
- **Особенности:**  
  - Работают с прошивками **Betaflight** или **INAV**.  
  - Подходят для высокоскоростного управления (до 32 кГц обновления PID).  

---

### **2. Программные прошивки (ОС для БПЛА)**
#### **ArduPilot (APM, ArduCopter, ArduPlane)**  
- **Описание:** Самая популярная open-source прошивка для БПЛА, поддерживающая мультикоптеры, самолеты, наземные и водные аппараты.  
- **Особенности:**  
  - Работает на **Pixhawk**, **Raspberry Pi**, **BeagleBone** и других платах.  
  - Поддерживает автономные миссии, геозаборы, RTK-GPS, оптический поток.  
  - Интеграция с наземными станциями: **Mission Planner**, **QGroundControl**.  

#### **PX4 Autopilot**  
- **Описание:** Еще одна мощная open-source прошивка, ориентированная на профессиональные приложения (например, промышленные БПЛА, исследования).  
- **Особенности:**  
  - Высокая точность навигации и расширенная поддержка датчиков.  
  - Интеграция с ROS (Robot Operating System) для робототехнических задач.  
  - Активно развивается сообществом и компаниями вроде Auterion.  

#### **Betaflight / INAV**  
- **Betaflight:**  
  - Прошивка для гоночных дронов, оптимизированная под высокую производительность (PID-контроль, настройка под гонки).  
  - Поддерживает OSD, Blackbox-логирование, управление ESC через DSHOT.  
- **INAV:**  
  - Расширение Betaflight для фиксированных крыльев и автономных миссий.  
  - Подходит для дальних полетов и аэрофотосъемки.

#### **Auterion SKYVOLT / Edge**

  - Поддержка ROS, Linux, безопасные коммуникации.  
  - Интеграция с облачными платформами (например, fortronOS).

### **Заключение**
Выбор контроллера зависит от задач:  
- Для **любительских проектов** подойдут **Pixhawk + ArduPilot/PX4**.  
- Для **гоночных дронов** — **Betaflight/INAV**.  
- Для **промышленных решений** — **DJI SDK** или **Auterion**.  
- Для **экспериментов с AI/ROS** — **Raspberry Pi + PX4**.  

Все современные системы поддерживают стандарты связи (MAVLink, CAN), что позволяет легко интегрировать дополнительные модули (LiDAR, оптические датчики, камеры).


Для разработки устройства, интегрируемого с дроном на базе ArduPilot, требуется реализовать двусторонний обмен данными по протоколу MAVLink через физический интерфейс UART. Детализация решения:

---

### 1. Получение телеметрии от дрона
#### Физический уровень:
- Интерфейс: UART (например, свободный порт TELEM2 на Pixhawk).
- Схема подключения:  
  Устройство ↔ Полетный контроллер:  
 
  GND → GND  
  TX (устройства) → RX (контроллера)  
  RX (устройства) → TX (контроллера)  
  VCC → 5V (если требуется внешнее питание)  
  
- Параметры UART:  
  Скорость: 57600/115200/921600 бод (должна совпадать с настройкой SERIALx_BAUD в ArduPilot).  
  Формат: 8N1 (8 бит данных, нет контроля четности, 1 стоп-бит).

#### Логический уровень:
- Протокол: MAVLink (версия 2).  
- Настройка потока данных:  
  В параметрах ArduPilot (SRx_*) задается частота отправки сообщений:  
 
plaintext

  SRx_POSITION = 10   # Позиция 10 Гц  
  SRx_ATTITUDE = 20   # Ориентация 20 Гц  
  SRx_RAW_SENS = 5    # Сырые данные сенсоров  
  
- Ключевые сообщения:  
  - GLOBAL_POSITION_INT (координаты, высота)  
  - ATTITUDE (крен, тангаж, рыскание)  
  - SYS_STATUS (состояние батареи, ошибки)  
  - GPS_RAW_INT (статус GPS).  

---

### 2. Передача команд управления на дрон
#### Физический уровень:
- Тот же UART-порт (двунаправленная связь).

#### Логический уровень:
- Эмуляция оператора:  
  Команды передаются как переопределение RC-сигналов через сообщение RC_CHANNELS_OVERRIDE (MAVLink #70).  
  Пример структуры:  
 
C

  mavlink_msg_rc_channels_override_pack(
      system_id, component_id, &msg,
      target_system,    // ID дрона (обычно 1)
      target_component, // ID компонента (автопилот = 1)
      chan1_raw,        // Канал 1: Roll (1000-2000 мкс)
      chan2_raw,        // Канал 2: Pitch
      chan3_raw,        // Канал 3: Throttle
      chan4_raw,        // Канал 4: Yaw
      0, 0, 0, 0, ...  // Остальные каналы (UINT16_MAX для игнорирования)
  );
  
- Важные нюансы:  
  - Частота отправки: ≥ 10 Гц, чтобы избежать активации FAILSAFE (при отсутствии команд > 0.5 сек).  
  - Каналы должны соответствовать настройкам ArduPilot (RCMAP_ROLL=1, RCMAP_PITCH=2 и т.д.).  
- Альтернатива: Высокоуровневые команды через SET_POSITION_TARGET_LOCAL_NED (требует режима GUIDED).  

---

### 3. Алгоритм работы устройства
1. Инициализация:  
   - Открыть UART-порт с указанной скоростью.  
   - Отправить запрос на поток данных (REQUEST_DATA_STREAM).  
2. Цикл обработки:  
  
Python

   while True:
       # Принять MAVLink-сообщение
       msg = mavlink_recv()  
       
       if msg.id == 'ATTITUDE':
           attitude = msg.roll, msg.pitch, msg.yaw
           
       if msg.id == 'GLOBAL_POSITION_INT':
           position = (msg.lat, msg.lon, msg.alt)
           
       # Вычислить команды на основе алгоритма
       throttle, roll = my_algorithm(attitude, position)
       
       # Отправить команды
       send_rc_override(roll, 0, throttle, 0)  # Пример для каналов 1 и 3
   
---

### 4. Требования к безопасности
- Failsafe-механизм:  
  Если устройство перестает отправлять команды > 0.5 сек, ArduPilot активирует режим RTL (Return-to-Launch).  
- Валидация команд:  
  Проверять выходные значения на диапазон 1000–2000 мкс.  
- Приоритет команд:  
  В ArduPilot команды от оператора с земли имеют приоритет над RC_CHANNELS_OVERRIDE (если только не включен параметр RC_OPTIONS=1).

---

### 5. Тестирование и отладка
- Симуляция: Использовать SITL (ArduPilot Software-in-the-Loop) с виртуальным COM-портом.  
- Инструменты:  
  - mavproxy для просмотра телеметрии.  
  - QGroundControl для мониторинга.  
- Логирование: Сохранять RAW-данные UART на SD-карту устройства.

---
### Схема архитектуры
[Устройство] 
    │   ↑ Команды RC_OVERRIDE (MAVLink) 
    UART ↓ Телеметрия (ATTITUDE, POSITION...) 
[Полетный контроллер (ArduPilot)] 
    │ 
    ├─→ Сенсоры (IMU, GPS...) 
    └─→ Исполняющие механизмы (моторы, сервы)
Реализация требует:  
- Библиотеки MAVLink (C/C++/Python).  
- Настройки параметров ArduPilot через Mission Planner.  
- Обеспечения низкой задержки (< 50 мс на цикл обработки).

### Решение для Betaflight Flight Controller

Для интеграции с Betaflight (популярным контроллером для гоночных дронов) требуется иной подход, так как Betaflight использует другие протоколы и архитектуру по сравнению с ArduPilot. Вот как организовать систему:

---

### 1. Получение телеметрии от дрона
#### Физический уровень:
- Интерфейс: UART (например, UART3 на F4/F7 контроллерах)
- Схема подключения:
 
  Устройство ↔ Betaflight Controller:
  GND  → GND
  TX   → RX (контроллера)
  RX   → TX (контроллера)
  VCC  → 5V/3.3V (в зависимости от платы)
  
- Параметры UART:  
  Скорость: 115200/400000 бод (зависит от протокола)  
  Формат: 8N1 (8 бит данных, нет контроля четности, 1 стоп-бит)

#### Логический уровень:
- Протокол: MSP (MultiWii Serial Protocol) или CRSF (Crossfire)
- Ключевые данные:
  - ATTITUDE (крен, тангаж, рыскание)
  - ALTITUDE (высота)
  - GPS (координаты, скорость)
  - BATTERY (напряжение, ток)
- Реализация MSP:
  - Устройство отправляет запросы в формате $M< (сигнатура MSP)
  - Пример запроса углов ориентации (ID 108):
   
C

    uint8_t msp_request[] = {0x24, 0x4D, 0x3C, 0x00, 0x6C, 0x00}; // $M< 0x6C
    
  - Ответ (пример):
   
Python

    [ '$', 'M', '>', 0x6C, data[0]...data[N], CRC ]
    
---

### 2. Передача команд управления
#### Физический уровень:
Тот же UART (двунаправленная связь)

#### Логический уровень:
Вариант 1: Эмуляция приёмника через CRSF (рекомендуется)
- Преимущества: Низкая задержка (<10 мс), высокая частота (150-333 Гц)
- Формат фрейма CRSF:
 
  [Адрес (0xEE)][Длина][Тип][Данные][CRC]
  
- Команды управления (RC Channels):
 
Python

  # Пример фрейма для 8 каналов:
  crsf_frame = [
    0xEE,       # Адрес полётного контроллера
    0x10,       # Длина (16 байт)
    0x16,       # Тип: RC Channels (0x16)
    ch1_lo, ch1_hi, ch2_lo, ch2_hi,  # Канал 1-2 (Roll/Pitch)
    ch3_lo, ch3_hi, ch4_lo, ch4_hi,  # Канал 3-4 (Throttle/Yaw)
    ...         # Каналы 5-16
    CRC         # Контрольная сумма
  ]
  
- Диапазон значений: 172-1811 (соответствует 988-2012 мкс в PWM)

Вариант 2: Команды через MSP (менее предпочтителен)
- Подходит только для высокоуровневых команд
- Пример установки углов:
 
C

  uint8_t set_attitude[] = {
    0x24, 0x4D, 0x3C, 0x08, 0xD9, 
    roll_lo, roll_hi, pitch_lo, pitch_hi, 
    yaw_lo, yaw_hi, 0x00, CRC
  };
  
---

### 3. Настройка Betaflight
1. В Betaflight Configurator:
   - Порты: Активировать "Serial RX" для выбранного UART
   - Configuration → Receiver: 
     - Протокол: "CRSF" (если используем CRSF)
     - Serial Provider: "CRSF" (для телеметрии)
2. CLI команды (если требуется):
  
   set serialrx_provider = CRSF
   set serialrx_inverted = OFF
   save
   
---

### 4. Алгоритм работы устройства
`python
import serial
import crc

# Инициализация UART
uart = serial.Serial("/dev/ttyS2", 400000)

# Функция отправки CRSF-команд
def send_rc_override(channels):
    frame = bytearray()
    frame.append(0xEE)  # Адрес
    frame.append(24)     # Длина (22 байта данных + 2 заголовка)
    frame.append(0x16)   # Тип: RC Channels
    
    # Упаковка 16 каналов (11 бит/канал)
    for ch in channels:
        frame.append((ch >> 8) & 0xFF)
        frame.append(ch & 0xFF)
    
    # Добавление CRC
    frame.append(crc.calculate(frame[2:]))
    uart.write(frame)

# Основной цикл
while True:
    # Чтение телеметрии (MSP или CRSF)
    data = uart.read()
    
    if is_msp_attitude(data): 
        attitude = parse_attitude(data)
        
    if is_crsf_gps(data):
        position = parse_gps(data)
    
    # Вычисление команд
    throttle, roll = autonomous_algorithm(attitude, position)
    
    # Формирование значений каналов (пример для AETR):

channels = [
        roll,       # Канал 1 (Roll)
        0,          # Канал 2 (Pitch)
        throttle,   # Канал 3 (Throttle)
        0,          # Канал 4 (Yaw)
        992,        # Канал 5 (Arm/disarm)
        *[992]*11   # Остальные каналы
    ]
    
    # Отправка команд
    send_rc_override(channels)

---

### **5. Критические отличия от ArduPilot**
1. **Частота обновления:**
   - Betaflight требует >150 Гц для RC-команд (vs 10-50 Гц в ArduPilot)
   - Задержка >20 мс может вызвать потерю управления

2. **Безопасность:**
   - **Failsafe:** Активируется через 0.2-0.5 сек без команд
   - **Arming:** Канал 5 должен быть >1800 для включения моторов
   - **Диапазоны:** Значения за пределами 172-1811 игнорируются

3. **Телеметрия:**
   - Нет автоматического потока данных
   - Требуются явные MSP-запросы или настройка CRSF-телеметрии

---

### **6. Тестирование и отладка**
- **Инструменты:**
  - Betaflight Configurator → Data Output
  - CRSF Sniffer (анализ фреймов)
  - Blackbox Explorer (лог полёта)
- **Симуляция:**
  - Использовать Betaflight-in-HIL с симулятором (VelociDrone, Liftoff)
- **Безопасное тестирование:**
  1. Проверять команды на выключенных моторах
  2. Использовать предварительный arming switch (канал 5)
  3. Начинать с малых значений управления

---

### **Рекомендуемая архитектура**
[Устройство]
     │
     UART (CRSF/MSP)
     │
[Betaflight Controller] 
 Требования к железу:
     └──→ ESC/Моторы
`
**Требования к железу:**  
- Микроконтроллер с UART >400 кбит/с (STM32, ESP32)  
- Тактовая частота >100 МГц для обработки на 150 Гц  
- Поддержка аппаратного CRC (для CRSF)

Использование CRSF обеспечит минимальную задержку и полную интеграцию, а MSP подойдёт для простых задач с низкой частотой обновления.
